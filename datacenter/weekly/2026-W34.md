# 2026-W34 週報：同一顆電池，同時掛在三個不同的結構上

第四份週報，本週 3 張卡——**是本軌跡目前產量最低的一週**，而且中間斷了三個工作日（8/19 三、8/20 四、8/21 五無卡片）。`dc-10` 是週日補的，且一寫就超標 14075 字元，就地拆出 `dc-10b`。

節奏先誠實記下來：**連續五週穩定的日更在本週斷了。** 佇列沒有落後太多（16/68），但斷鏈的位置很不巧——W33 週報明確要求「`DeviceRegistry` 必須在 `dc-10` 之前」，結果 `dc-10` 到了，registry 沒到。這筆帳本週不但沒清，還被三張卡各推了一把，形狀反而變大了（見下面連貫性檢視 #2）。

不過本週的內容密度補回了數量。三張卡看起來毫不相干——電池怎麼量、鋰電放哪裡、STS 怎麼切——**但它們是同一件事的三個切面：同一顆電池、同一台 UPS，同時是三個不同結構上的節點，而每個結構問的「上游是誰」都不一樣。**

## 本週卡片

| 卡 | 標題 | 這張卡最關鍵的一個事實 |
|---|---|---|
| `dc-09b` | [電池測試制度（IEEE 1188）](../devices/battery-testing-regime.md) | **同一筆內阻讀值同時是「該汰換」與「不能索賠」**（35.9% 對 20% / 30–50% / 50% 三條門檻）。而且換個分母（baseline → 串平均），35.9% 變 **14.5%**，判定完全翻轉——**分母必須是欄位** |
| `dc-09c` | [鋰電消防合規（NFPA 855 / UL 9540A）](../devices/lib-fire-compliance.md) | **消防樹上 2N 是把可燃能量翻倍**——安全性的方向在電力樹與消防樹上**相反**。而 `25% LFL = 10,000 ppm`，off-gas 工作在 ppm–ppb，**差三到四個數量級**：把 LFL 當早期預警，是把「快爆了」標成「注意一下」 |
| `dc-10` | [靜態切換開關 STS](../devices/static-transfer-switch.md) | **「有兩個源」是宣稱，不是事實。** 至少四件事會讓冗餘歸零卻不改變儀表板上任何數值，其中 `SCR Shorted` 是 **latched**——它會被人 ack 掉，但進線開關還是跳開的 |

## 串起來

### 一、本週真正的主題：三張卡各住在一個不同的結構上

前三週的卡片都住在同一棵樹上——電力樹，往上找誰餵誰。本週三張卡**沒有一張是這樣**：

| 卡 | 它住在什麼結構上 | 這個結構的「上游」是什麼 | 遍歷的目的 |
|---|---|---|---|
| `dc-09b` | **時間軸上的鏈** | 上一筆讀值、以及 baseline | 算趨勢偏離 |
| `dc-09c` | **空間樹**（`FireCompartment`，有階層） | 所屬防火區劃 | **聚合**能量 |
| `dc-10` | **電力圖**——第一次是 DAG 不是樹 | 兩條邊，恰好一條導通 | 找源頭 |

`dc-09b` 卡片自己就寫了這句話：「它是一條**時間軸上的鏈**，不是空間上的鏈。」`dc-09c` 接著說：「**兩棵樹共用節點、邊完全不同。**」而 `dc-10` 補上第三個：STS 有兩條合法上游、恰好一條導通，且**當下是哪一條會在毫秒級變動**。

**於是同一台 UPS 電池組，在同一個星期裡被證明是三個不同結構上的節點。** 這件事直接判了兩個常見設計的死刑：

```
Device.upstream_id: str      ← dc-10 打死（兩條邊，一條導通）
Device.fire_zone:   str      ← dc-09c 打死（區劃有階層，且要遞迴聚合）
BatteryString.baseline_mohm  ← dc-09b 打死（baseline 是版本化實體，換儀器就作廢）
```

三個都是「把關係塞進節點的一個欄位」。**三張卡、三種關係、同一個錯誤。**

### 二、冗餘這個欄位，本週死了三次，而且有一次符號是相反的

`redundancy = "2N"` 這種字串欄位，前三週只是「不精確」，本週變成「會害人」：

| 卡 | 對冗餘做了什麼 | 嚴重程度 |
|---|---|---|
| `dc-09b` | 測試期間冗餘是**負的**：容量測試要把串拉離線，N+1 的 UPS 群組實際配 N−1 的電池；連量內阻都要離線才準 | 暫時性降級 |
| `dc-10` | STS 本體是**單點**；「兩個源」隨時可能因 `transfer_inhibit`／latched SCR 故障／維修旁路而歸零 | 宣稱與事實脫鉤 |
| `dc-09c` | 消防樹上 **2N 是把同一空間的可燃能量翻倍**——冗餘讓事情**更危險** | **符號相反** |

第三列是本週最反直覺的一行，值得停下來：

```
電力樹：  多一路 → 可用度上升   （2N 比 N 好）
消防樹：  多一路 → 可燃能量翻倍 （2N 比 N 危險）
```

**同一個「2N」，在兩棵樹上的價值符號相反。** 唯一同時滿足兩者的做法是把冗餘路徑放進**不同防火區劃**——而這件事在單線圖上完全看不出來，只在建築平面圖上看得到。

這也讓 W33 那句「用數量冒充獨立性」升級了。過去三次（`dc-01` 兩路市電同變電所、`dc-05` 三台機共用油管、`dc-08` 旁路同源）講的都是**電力上的共祖**；`dc-09c` 是第四次，但共的不是電源，是**空間**。`dc-10` 的自我檢核第 4 點又預告了第五次（STS 兩條輸入往上追是同一面盤），留給 `dc-10b`。

> **收斂到一句話**：`redundancy` 不是設備的欄位，是**「在哪一棵樹上、往上追到哪裡才分開」的查詢結果**。而且答案要帶著共同祖先清單，不能是布林。

### 三、「你憑什麼說它現在是好的」——第三種答案本週出現

W33 建立了一張表：凡是只有故障當下才會被用到的功能，都必須有測試日期欄位。本週把這張表補完成三類，而且 `dc-10` 卡片自己就把它寫出來了：

```
測試型  ：last_verified_at 過期  → 「你不知道它還行不行」   （dc-05c / dc-06 / dc-07b / dc-09b）
可算型  ：Isc(config) > Icw      → 「這個配置本身違規」       （dc-07b / dc-09c 能量閘門）
latched ：曾經壞過且沒人來修      → 「它現在確實是壞的」       ← dc-10 新增
```

三者的共同點是**都不能只看即時遙測算出來**，但差別很重要：

- **測試型**是「未知」——資料庫誠實承認自己不知道。
- **可算型**是「已知違規」——不必等故障，枚舉配置就知道，而且正確歸宿是互鎖不是告警。
- **latched 型**是「已知損壞」——而且**它是歷史的函數，不是狀態的函數**。

`dc-10` 的 SCR 短路是本軌跡第一個 latched 告警，它逼出一個之前沒人想過的問題：**告警第一次反過來成為狀態計算的輸入。** `redundancy_effective()` 必須讀 latched 告警才算得出來——告警不再只是輸出。

而這件事有一個很尖銳的操作面後果：**latched 告警被 ack 之後仍然 active。** 允許 ack 消掉它，等於允許一個人用一次點擊，把「這台 STS 沒有冗餘、其中一側進線開關是跳開的」變成看不見。W33 才剛提出的 `Alarm(severity, code, message, entity_ids, raised_at)` **裝不下這個** ——提出後一週就被推翻（見連貫性檢視 #1）。

### 四、三張卡三個來源分歧，命中率 100%

W33 說「本軌跡第一次連續兩張卡出現來源分歧」。本週是**三張卡三個分歧**，而且形狀各不相同：

| 卡 | 分歧 | 分歧的本質 |
|---|---|---|
| `dc-09b` | 內阻汰換門檻 **20% / 30–50% / 50%**，分母還分 baseline vs 串平均 | **三種立場**：保守營運 ／ 工程指引 ／ 商業契約 |
| `dc-09c` | NFPA 855 **2023 版有能量表、2026 版把表移除改 HMA 預設**，IFC 2024 仍引 2023 版 | **同一份規範的兩個時間切面**，且會並存好幾年 |
| `dc-10` | 同一類設備 MTBF：Schneider WP 62 說 **40 萬–100 萬小時**，PDI 規格書說 **超過 200 萬小時** | **邊界畫在哪裡不同**（整台 vs 關鍵輸出匯流排），且相隔七年 |

前三週的分歧都是「兩個數字量的不是同一件事」。本週多了兩種新形狀：**時間版本**（`dc-09c`）與**利益立場**（`dc-09b` 的保固門檻、`dc-10` 的「一邊說別裝、一邊賣給你」）。

**三種形狀的處置方式不同，這很重要：**

- 「量不同東西」→ 拆成兩個欄位（`design_life` vs `service_life`）。
- 「時間版本」→ 門檻變成**版本化的資料列**（`CodeRule.edition`）。
- 「利益立場」→ 門檻變成**帶來源的策略列**（`ThresholdPolicy.source`），且**多筆並存**，一筆事實 fan-out 成多筆判定。

後兩者其實是同一張表的兩個欄位。`dc-09b` 與 `dc-09c` 隔一天各自發明了一套，形狀幾乎逐項對應——這是本週最該立刻收斂的一項（連貫性檢視 #3）。

### 五、電力鏈的位置：本週走到 UPS 下游第一站

```
市電 dc-01 → MV dc-03 → 變壓器 dc-02 ─┐
                                       ├→ ATS dc-04 → LV 主盤 dc-07 → UPS dc-08 → ★ STS dc-10 →（dc-11 PDU）
燃料 dc-06 → 發電機 dc-05 ─────────────┘        ↑                        ↑                ↑
                                          [保護層 dc-07b]         [電池 dc-09]      單路設備
                                                                   ├ 測試制度 dc-09b（時間軸）
                                                                   └ 消防合規 dc-09c（空間樹）
```

三件事值得注意：

**（1）`dc-09b` 與 `dc-09c` 在這張圖上「掛不上去」，這正是重點。** 它們沒有上游也沒有下游——一個往時間軸長，一個往空間樹長。**能畫進單線圖的東西，本軌跡已經走完一半了；接下來的知識愈來愈多是畫不進單線圖的。**

**（2）STS 是全鏈第一個「兩條上游同時活著」的節點。** `dc-04` ATS 也有兩個源，但市電與發電機**通常一邊是死的**，而且切換是秒級、有機械位置可讀。STS 兩邊同時帶電、切換是毫秒級、SCR 沒有可見的物理位置——**「現在通的是哪一條」只能從事件記錄還原，不能從現場目視確認。** 這是 `upstream_id` 撐到第十張卡才崩掉的真正原因（本週間隔複習就考這題）。

**（3）冷卻鏈的欠款還在，而且本週多了一筆新的。** `dc-09c` 演算 4 要求排風機掛在發電機盤上（NFPA 855 2026 版 §4.10），這是**消防系統對電力樹提出的容量需求**——W32 留下的「冰水主機接 UPS 還是直吃發電機」那題，現在多了一個同方向的鄰居。兩題應該一起問。

## 自我測驗

**Q1（事實回憶）. 某 12 V block 的內阻 baseline 是 3.20 mΩ，本季量到 4.35 mΩ。這顆該不該換？能不能跟廠商索賠？**

??? note "答案"
    **該換，但索賠會被打回——而且如果換個分母，連「該換」都不成立。**

    ```
    分母 = baseline：   (4.35 − 3.20) / 3.20 = 35.9%
    分母 = 串平均 3.80：(4.35 − 3.80) / 3.80 = 14.5%   ← 判定翻轉
    ```

    以 baseline 為分母的 35.9% 對上三條門檻：

    | 門檻 | 出處 | 判定 |
    |---|---|---|
    | **20%** | CPBS 引 IEEE 1188 較新版本 | 超標 → **排汰換** |
    | **30–50%** | IEEE 1188-2005 Annex C.4 原文「typically a change of 30% to 50%… is considered significant」 | 灰帶 → 加測、追趨勢 |
    | **50%** | 廠商保固索賠 | 未超標 → **索賠被打回** |

    **同一筆讀值同時是「該汰換」與「不能索賠」。** 這不是資料品質問題，是三個門檻服務三個不同目的：安全裕度、工程指引、商業契約。

    **對你的模型**：門檻是策略資料不是常數——`ThresholdPolicy(kind, source, denominator, pct, action)`，多筆並存；`denominator ∈ {baseline, string_avg}` 必須是欄位。一筆讀值對多條策略求值，產出多筆 `Finding`。**判定不是量測的屬性，是量測與策略的笛卡爾積。**

    再補一個容易漏的前提：這一切的前提是 **baseline 在投入服務約 6 個月後量過**（新電池尚未完全化成，出廠讀值不能用；型錄值更不能用）。沒有那筆，IEEE 1188 原文說後續讀值 "difficult to interpret and of limited value"——而且**不可回溯補救**。

**Q2（事實回憶）. 電池室裝了 25% LFL 氫氣偵測器並接進告警系統。有人說「早期預警有了」。錯在哪？順便說出你模型裡的 kWh 是哪一個 kWh。**

??? note "答案"
    **量級差三到四個數量級，而且方向完全反了。**

    ```
    氫氣 LFL ≈ 4 vol%
    25% LFL = 0.25 × 4% = 1 vol% = 10,000 ppm
    off-gas 偵測器工作範圍：ppm — ppb
    ```

    等 LFL 偵測器動作，房裡的氫氣已累積到 off-gas 門檻的**一萬倍**——電池早就在排氣了。**25% LFL 不是早期預警，是防爆的最後緩衝（4:1 安全係數）。** 真正的預警窗口可達數十分鐘，用來停充、隔離、啟動排風，而只有 ppm 級 off-gas 看得到它。NFPA 75（2024 版）首次為鋰電 UPS 加入 off-gas 偵測要求，正是因為傳統可燃氣體感測器**不是合適的替代品**。

    **kWh 的部分**：合規一律用**銘牌最大儲能**，不是可用容量。接 `dc-09` 的 bank：

    ```
    usable  = 28.0 kWh（已扣 80% DoD）  ← 你模型裡多半存的是這個
    nameplate = 28.0 / 0.8 = 35.0 kWh   ← 消防要的是這個
    2N、每路 2 個 bank → 4 × 35.0 = 140 kWh（不是 112.0）
    ```

    差 20% 剛好足以讓一個「算起來 580 kWh、以為過了 600」的設計實際上是 **725 kWh**。

    **對你的模型**：`nameplate_energy_kwh` 與 `usable_energy_kwh` 必須是兩個欄位；偵測器要有 `detector_class ∈ {off_gas, lfl, smoke, thermal, bms}`，**告警動作與時間預算綁在 class 上**——塞進同一張 alarm 表用同一套嚴重度分級，等於把最有價值的那三十分鐘丟掉。

**Q3（應用）. 廠商說「STS 轉換 4 ms，遠低於 IT 設備 20 ms 容忍度，絕對安全」。把最壞情況算出來，然後說出這句話為什麼不是這台設備能保證的。**

??? note "答案"
    **餘裕從 13.83 ms 掉到 3.00 ms——剩原本的 21.7%。**

    先看 1/4 cycle 到底幾毫秒（頻率決定），以及廠商通常提供**兩種演算法**，第二種是刻意慢的：

    | | 1 cycle | 1/4（快速 POG） | 3/4（抗湧流 VSS 最壞） |
    |---|---|---|---|
    | **60 Hz（台灣、美規）** | 16.67 ms | **4.17 ms** | **12.50 ms** |
    | 50 Hz（歐洲、中國） | 20.00 ms | 5.00 ms | 15.00 ms |

    容忍度取 WP 62 實測**重載** SMPS 的 18 ms（比 ITIC 的 20 ms 誠實）：

    ```
    60 Hz + POG ：18 − 4.17  = 13.83 ms
    60 Hz + VSS ：18 − 12.50 =  5.50 ms
    50 Hz + VSS ：18 − 15.00 =  3.00 ms
    ```

    **三個把餘裕吃掉的變數，沒有一個住在 STS 身上：**

    1. **演算法設定**——下游若是變壓器型 PDU，快速轉換會讓磁通不連續而產生湧流，必須開抗湧流（1/4 → 3/4 cycle）。**轉換時間是設定值不是規格值，而決定它的是下游有沒有變壓器。**
    2. **市電頻率**——型錄那個「4 ms」通常是 60 Hz 的數字。
    3. **下游負載率**——18 ms 是重載實測，輕載長很多，但不能拿輕載數字做設計。

    **對你的模型**：`transfer_time_ms = 4` 這個欄位，會在有人為了下游 PDU 切成抗湧流那天起開始說謊。它是 `algorithm × line_hz × downstream_has_transformer × load_pct` 的函數——跨設備規則，跟 W33 那條「電池 runtime > 發電機起動時間」同形，掛在任何單一設備上都寫不出來。

**Q4（應用）. STS 儀表板顯示「Source 1 正常、Source 2 正常、負載 45%、目前在 Source 1」。這台 STS 現在有冗餘嗎？再往外一層：本週三張卡對「冗餘」各說了什麼？**

??? note "答案"
    **從畫面上看不出來。** 至少四件事會讓冗餘歸零，卻不改變上面任何一個數值：

    1. **`Transfer Inhibit` 生效中**——下游大電流（PDI 出廠設在約 **3 倍**額定；600 A 機 ≈ 1800 A）時邏輯禁止轉換，Source 2 再健康也切不過去。
    2. **`SCR Shorted` latched 未 reset**——系統已跳開其中一側進線開關，實際只剩一個源，但「兩個源都正常」仍為真。
    3. **維修旁路關閉中**——電子元件被隔離，**沒有自動轉換**。
    4. **兩條輸入在上游合流**——追到底是同一台 UPS 或同一面盤。這項**連遙測都不會變**，是設計缺陷不是狀態（留給 `dc-10b`）。

    順帶把演算 2 的結論接上：下游一顆分路 bolted fault（用 `dc-07b` 那筆 50.6 kA 概算）遠超 1800 A 抑制門檻，**STS 立刻凍結、把自己當導線**，只能等上游斷路器清除——有選擇性協調約 **0.3 s**，開 ERMS 約 **0.05 s**，兩個都遠超 ITIC 的 20 ms。**下游故障期間「兩個源」一點忙都幫不上**，但抑制邏輯是對的：它用「這段時間不保護」換「不要把下游短路接到另一條健康母線」。

    **三張卡對冗餘各說了一句：**

    ```
    dc-09b：測試期間冗餘是負的      （容量測試要拉離線，N+1 UPS 配 N−1 電池）
    dc-10 ：冗餘是宣稱不是事實      （四件事讓它歸零，畫面全綠）
    dc-09c：冗餘的符號在消防樹上相反 （2N = 同空間可燃能量翻倍）
    ```

    **對你的模型**：不能有 `source_count = 2` 餵給任何告警規則，只能有把前三項納入的 `redundancy_effective()`；第四項靠拓撲比對產出**稽核報表**（它不會變化，所以不是告警）。而 `redundancy` 這個欄位本身要退位——它必須帶著「在哪棵樹上」與「共同祖先是誰」。

**Q5（建模判斷）. 本週三張卡分別住在時間鏈、空間樹、電力圖上。`DeviceRegistry` 該長什麼樣？以及——本週有一個地方讓「告警」這個概念發生了性質變化，是哪裡？**

??? note "答案"
    **第一部分：registry 不是 `dict[str, Device]`，是一個多重關係圖。**

    三種關係並存，共用節點，邊完全不同：

    ```python
    registry.upstream(device)            # 電力：DAG（STS 起有兩條邊，恰好一條 energized）
    registry.fire_compartment(device)    # 空間：樹（有階層，要遞迴聚合 nameplate kWh）
    registry.readings(device, since=...) # 時間：鏈（分組鍵是 instrument_id，跨儀器不可比）
    ```

    三個具體約束，各來自一張卡：

    - **邊要有身分**（`dc-10`，本軌跡**第四次**點名——前三次是 `dc-03b` 互鎖、`dc-05c` ATS 輪替、`dc-07b` 選擇性）。`PowerEdge(id, src, dst, role: PREFERRED|ALTERNATE, energized)`。`active_source` **是邊的狀態，不是節點的欄位**，而且它的真相在事件記錄裡，節點上的欄位只能當 last-known cache。
    - **空間樹要能遞迴**（`dc-09c`）。`fire_zone: str` 遇到「區劃有階層」就崩，而聚合必須用 `nameplate` 不是 `usable`。
    - **時間鏈要有分組鍵**（`dc-09b`）。`instrument_id` 與 `method` **不是稽核欄位，是 trend 的分組鍵**——跨儀器比較無效，查詢層要能**拒絕**，回「無法判定」而不是回「判定為好」。

    最後這點值得單獨記：**「無法判定」跟「判定為好」是兩件事。** 這是 W33 `Bound`／`UNKNOWN` 那條規則在本週的第二個落點。

    **第二部分：告警第一次反過來成為狀態計算的輸入。**

    前九張卡的告警都是**狀態的函數**——`f(現在的量測)`，條件為真就叫、消失就停，可以安全 ack。`dc-10` 的 latched SCR 故障不是：

    ```
    前九張卡： 量測 → 規則 → 告警          （告警是純輸出）
    dc-10  ： 量測 + latched 告警 → 狀態    （告警是輸入）
                └ redundancy_effective() 必須讀 latched 告警才算得出來
    ```

    它是**歷史的函數**——`f(曾經壞過, 有沒有人來修)`。所以 `Alarm` 要長出 `latched` / `acked` / `reset_at` / `reset_by`，且 **`ack()` 對 latched 告警不得改變 `active()`**。這條約束不是潔癖：ack 之後設備仍只剩一個源、進線開關還是跳開的，**允許 ack 消掉它，等於允許一個人用一次點擊把「這台 STS 沒有冗餘」變成看不見。**

    > 一句話總結本週的建模躍遷：**W31「一個欄位裝不下一個事實」→ W32「有些事實不住在欄位裡」→ W33「有些答案是一個數加上它的來歷」→ W34「同一個節點同時活在多個結構裡，而『上游是誰』要先問『在哪棵樹上』」。**

## 間隔複習

依 W33 排定的表：**W34 抽兩週前（W32，`dc-04` ~ `dc-05c`），四週前（W30）尚無卡片。**

抽中 **`dc-05c` NFPA 110 定期測試制度與 30% 門檻**（W32，2026-08-07）。挑它不是隨機——**它跟本週兩張卡犯的是同一個錯，而且三次的錯誤方向完全一致。**

**複習題（W32 `dc-05c` × 本週 `dc-09b` / `dc-09c`）. 維護商交來月測報告：「負載 700 kW，連續 45 分鐘，符合 NFPA 110」。這台是 Cummins DQLF——ESP 2750 kW、COP 2100 kW、場址降載後 2393 kW。過了嗎？然後說出這題跟本週兩張卡的共同形狀。**

??? note "答案"
    **不合規，而且報告上那個「合規」正是問題本身。**

    ```
    正解  ESP standby 銘牌：2750 × 30% = 825 kW  → 700 kW 只有 25.5%，不過
    誤用  COP           ：2100 × 30% = 630 kW  → 700 就過了   ← 最可能的來源
    誤用  場址降載      ：2393 × 30% = 718 kW  → 仍差 18 kW
    ```

    NFPA 110 §8.4.2 原文是「不少於 **EPS standby nameplate kW rating** 的 30%」，兩個修飾詞都關鍵：**standby**（就是 ESP，`dc-05` 五個額定裡**最大**的那個）、**nameplate**（**不套場址降載**）。

    另外「跑 45 分鐘」不能補償負載不足——**時間與負載是 AND 不是 OR**（門檻是 30 min **且** ≥30%）。

    **誤差方向永遠偏小**，因為 ESP 是五個額定裡最大的、銘牌又大於場址值。所以選錯分母不是保守，是**你以為合規、實際長期輕載**——正是 wet stacking 的成因。**這是全鏈唯一一個「合規文件本身會掩蓋物理劣化」的地方。**

    ---

    **共同形狀：三張卡、三個分母、同一個方向。**

    | 卡 | 正確分母 | 常見誤用 | 判定怎麼變 |
    |---|---|---|---|
    | `dc-05c` | ESP standby 銘牌 **2750 kW** | COP 2100 ／ 場址 2393 | 門檻 825 → 630，**紅變綠** |
    | `dc-09b` | commissioning baseline **3.20 mΩ** | 串平均 3.80 mΩ | 35.9% → **14.5%**，**紅變綠** |
    | `dc-09c` | nameplate **35.0 kWh** | usable 28.0 kWh | 140 → **112 kWh**，**紅變綠** |

    三次都是**換個分母，判定就從「該處理」翻成「沒事」**，而且三次都不會有任何告警——**分母不是量測出來的，是被選出來的，而選錯不留痕跡。**

    **對你的模型**（三層，缺一不可）：

    1. **分母必須是欄位**，不能是呼叫端的隱含假設：`Policy.basis ∈ {esp_nameplate, baseline, string_avg, nameplate_kwh, usable_kwh}`（連貫性檢視 #3 那張表就是為此而存在）。
    2. **求值函式要求顯式傳入分母，沒傳就 raise**——跟 `dc-09b` 的「跨儀器比較要 raise 不是回 0」同一個設計動機：**無法判定 ≠ 判定為好。** 給預設值等於把某次的選擇燒進所有歷史資料。
    3. **`Finding` 要記下用了哪個分母**，否則三個月後沒有人能回答「這份報告當初是拿什麼算的」——而這正是你**現在**要拿去問維護商的問題（見本週 Q1）。

    > 順帶一提，`dc-05c` 還有第二層值得複習：**避免 wet stacking 的最低負載，法規寫 30%、廠商普遍寫 40%**。兩邊不是誰錯——**30% 是法規最低門檻，40% 是工程建議值**。含意是：**照 30% 測是合規的，但不保證不 wet stacking。** 這跟本週 `dc-09b` 的「IEEE 20% vs 保固 50%」是完全同一個形狀：**合規門檻與工程門檻是兩條策略，必須並存。**

**四週前（W30）：尚無。** 本軌跡起始於 2026-07-28。**W35 起雙軌全開**（同時抽兩週前 W33 與四週前 W31），屆時每份週報多一題。

### 🔴 1. `Alarm` 的形狀在提出後一週就被推翻

W33 剛建議 `Alarm(severity: Severity, code: str, message: str, entity_ids: list[str], raised_at)`，`dc-10` 的 latched SCR 告警**裝不下**——那個設計預設「告警隨條件消失」。

```python
@dataclass
class Alarm:
    code: str; severity: Sev; message: str; entity_ids: list[str]
    raised_at: datetime
    latched: bool = False              # ← dc-10 新增
    acked: bool = False
    reset_at: datetime | None = None   # ← reset 是有人負責的動作，不是條件變化
    reset_by: str | None = None

    def active(self) -> bool:
        if self.latched:
            return self.reset_at is None    # ★ 與當前條件無關
        return self._condition_holds()

    def ack(self) -> None:
        self.acked = True                   # ★ 刻意不碰 active()
```

**兩個設計決定要說清楚：**

1. **`ack()` 不得改變 `active()`。** 這是整項的核心，也是唯一一個「不修就會有人受害」的地方——ack 之後 SCR 還是壞的、進線開關還是跳開的。
2. **`active()` 對 latched 者不看條件。** 這打破了「告警是量測的純函數」這個從第一張卡沿用到現在的假設。

**連帶影響**：`redundancy_effective()` 要讀 latched 告警，於是**告警第一次成為狀態計算的輸入**。這代表 registry 與告警引擎不能是單向依賴——需要想清楚求值順序，否則會繞成循環。**建議第一個做，因為它同時是本週唯一的安全性缺陷。**

### 🔴 2. `DeviceRegistry` 的形狀確定了，但比 W32 設想的大得多

W32 提出時想的是「把散落的 `Genset` / `Ups` / `BatteryBank` 收進一個字典 + `upstream()` 遍歷」。本週三張卡把它撐成三種關係：

| 關係 | 結構 | 來自 | 遍歷目的 |
|---|---|---|---|
| `upstream()` | **DAG**（不是樹） | `dc-10` | 找源頭、算共祖 |
| `fire_compartment()` | 樹（有階層） | `dc-09c` | **遞迴聚合能量** |
| `readings()` | 鏈（分組鍵 `instrument_id`） | `dc-09b` | 算趨勢偏離 |

**這不是三個 registry，是一個 registry 的三種邊。** 節點共用（同一顆電池同時出現在三者裡），所以拆成三個物件會立刻產生同步問題。

**收斂建議**（最小可用版本，約 40 分鐘）：

```python
@dataclass(frozen=True)
class PowerEdge:
    id: str
    src_id: str
    dst_id: str
    role: Role                 # PREFERRED | ALTERNATE | SOLE
    energized: bool = True     # last-known；真相在 TransferEvent

class DeviceRegistry:
    nodes: dict[str, Device]
    power_edges: list[PowerEdge]           # DAG
    compartments: dict[str, FireCompartment]   # 樹，node.compartment_id 指過去

    def upstream(self, device_id) -> list[PowerEdge]: ...
    def ancestors(self, device_id) -> set[str]: ...        # ← dc-10b 要用
    def compartment_chain(self, device_id) -> list[str]: ...
```

`ancestors()` 是為 `dc-10b` 預留的：**「兩條輸入是否真獨立」= 兩條路徑的 `ancestors()` 是否互斥**，而回傳值必須是**共同祖先集合**不是布林。這一個方法會同時抓出 `dc-01` 兩路市電同變電所、`dc-05` 三台機共用油管、`dc-08` 旁路同源、`dc-10` STS 兩輸入同盤——**四個既有的坑，一段程式碼。**

**`dc-10b` 的動手練習就是這個，所以它必然會被做出來。** 但 #1 的 `latched` 建議先做，因為 `redundancy_effective()` 要用。

### 🟡 3. `ThresholdPolicy` 與 `CodeRule` 是同一個形狀，隔一天各寫了一套

W33 的 `FuelTank` / `BatteryString` 同構問題隔了四天才被發現；本週這兩個**隔 24 小時**：

| 概念 | `dc-09b` `ThresholdPolicy` | `dc-09c` `CodeRule` |
|---|---|---|
| 判準來源 | `source ∈ {IEEE, VENDOR_WARRANTY, INTERNAL}` | `edition ∈ {NFPA855_2023, NFPA855_2026, TW_ESS_GUIDE}` |
| 適用範圍 | `kind ∈ {ohmic, capacity}` | `scope ∈ {unit, group, compartment}` |
| 分母／基準 | `denominator ∈ {baseline, string_avg}` | （隱含在 scope 的聚合方式） |
| 門檻 | `pct` | `limit_kwh`（**可為 None** = 該版本移除此表） |
| 動作 | `action` | `requires_hma` |
| 輸出 | `list[Finding]` | `list[Finding]` |

**兩張卡的自我檢核 Q3 甚至寫了同一句話**：「判定不是事實的屬性，是事實與判準的笛卡爾積。」

**收斂建議**：一個 `Policy` + 一個 `Finding`。

```python
@dataclass(frozen=True)
class Policy:
    id: str
    kind: str                      # ohmic | capacity | stored_energy | separation
    source: str                    # ieee | vendor_warranty | internal | nfpa855_2023 | tw_guide
    jurisdiction: str | None       # 法規類才有
    basis: str | None              # baseline | string_avg | nameplate | usable  ← 分母
    limit: float | None            # None 有意義：該版本已移除門檻
    action: str

@dataclass(frozen=True)
class Finding:
    fact_id: str
    policy_id: str                 # ★ 一定要留，才印得出「同一座機房、三套規則」對照表
    verdict: str                   # PASS | FAIL | NOT_IN_SCOPE | REQUIRES_HMA | UNKNOWN
```

`limit=None` 這一格別當成缺漏——它是 NFPA 855 2026 版**刻意移除能量表**的忠實表達，求值時不比大小而是直接回 `REQUIRES_HMA`。**能誠實表達「這條規則在這一版不存在」，是這張表存在的理由之一。**

### 🟡 4. 「型錄值 vs 實際值」已經出現三次，該升級成通則

```
dc-09 ：design_life_years    vs service_life_est_years    （10 年 vs 5.8 年）
dc-09c：nameplate_energy_kwh vs usable_energy_kwh         （35.0 vs 28.0）
dc-09b：型錄內阻值           vs 6 個月後量的 baseline      （明確禁止用前者）
```

三次、三個不同的量、同一條規則。而且 `dc-09b` 演算 2 示範過踩到它的代價：**排程演算法讀錯欄位，會安靜地遲到三年**，沒有任何告警。

**收斂建議**：訂成專案級規則寫進 `CLAUDE.md`——

> **凡是同時存在「型錄／設計／銘牌值」與「實際／估算／量測值」的量，一律兩個欄位，且欄位名要能一眼分辨（`_rated` / `_est` / `_measured` 後綴）。使用端不得自行換算。**

順便和 W32 #6（單位後綴 `_s` / `_ms` / `_min`）、W33 #6（動詞 `usable_*`）合併成**一次 rename**。三筆都是純機械改動，分三次做比較貴。

### 🟡 5. `redundancy` 作為欄位，第三次死亡（本週符號還相反了一次）

不重複展開（見「串起來」第二節）。結論是 `redundancy` 不能是設備上的字串欄位，必須是帶樹別與共祖清單的查詢結果：

```python
def effective_redundancy(registry, load_id, tree: Tree) -> tuple[int, set[str]]:
    """回 (獨立路徑數, 共同祖先集合)。共祖非空 → 宣稱的冗餘是假的。"""
```

`tree` 參數不是過度設計：**`Tree.POWER` 與 `Tree.FIRE` 的答案可能相反**（`dc-09c`），而 `dc-10b` 的動手練習正好要實作前者。

## 本週該問 facility 的問題

三張卡共提出 8 個問題，去重後選 3 個**下週真的拿去問人**的。挑選標準沿用前三週：「**現在問還來得及改，晚問就固化了**」。本週三題的固化時點分別是——**已經在流逝／設計階段／commissioning**。

### Q1 — 問 **電池供應商 / 維運**（🔴 最急：這題的答案每天都在變差，且不可回溯）

> 「這批電池的**內阻 baseline 是誰量的、哪一天、用哪一台儀器**？有沒有**投入服務滿 6 個月**之後量的那一筆？量的時候有沒有記 cell 表面溫度、浮充電壓、充電電流？讀值有沒有校正到 25 °C？
> 保固索賠**認的分母是 baseline 還是 string average、門檻幾 %**？需要幾筆週期讀值才受理？
> 另外——**上一次容量測試是哪一天、測出百分之多少？** 那天的**再充電**花了多久？

**為什麼是這題，而且為什麼最急**：

- **這是本軌跡至今少數幾件真正有時效性的事，跟 commissioning 同一類。** baseline 必須在電池完全化成後、劣化開始前那個窗口量，**錯過就永遠補不回來**。現在去量，量到的是「已經劣化過的狀態」，之後所有偏差都以它為零點——趨勢會永遠低估。
- **沒有 baseline，你可以有一整年的高頻 BMS 遙測卻在索賠時被打回**，因為缺一筆兩年前該量而沒量的數字。IEEE 1188 原文說沒有 baseline 的內阻讀值 "difficult to interpret and of limited value"。
- **分母那題決定內部門檻怎麼訂。** 35.9% 換個分母變 14.5%，判定完全翻轉。不問清楚，你的告警規則和廠商的受理標準會長期不一致，而你要到索賠那天才知道。
- **順帶問出儀器型號**：換一台儀器 = baseline 作廢。`instrument_id` 是 trend 的分組鍵，不是稽核欄位。

### Q2 — 問 **消防設備師 / 建築師 / AHJ**（⚠️ 設計階段固化，蓋完就是拆牆）

> 「**A 路與 B 路的電池在不在同一個防火區劃？時效幾小時？平面圖在哪？**
> **AHJ 採用哪一版——NFPA 855 的 2023、2026，還是只走台灣『提升儲能系統消防安全管理指引』？**
> 我們一個區劃的**銘牌總儲能**是 140 kWh（不是 112——那是扣過 DoD 的可用值）。2023 版三道閘門（unit 50／group 250／fire area 600 kWh）都過，但 2026 版**移除了這張表、改成 HMA 預設**，要註冊專業技師主導、還多一項大型燃燒試驗（LSFT）。我們要守哪一套？
> 廠商那份 **UL 9540A 報告測到第幾層**（cell / module / unit / installation）？
> **排風機與 off-gas 偵測盤掛在哪一路電源、有沒有進發電機盤？**」

**為什麼是這題**：

- **「A/B 在不在同一區劃」是本週最便宜、後果最大的一題。** 若同區劃，**2N 在消防事故上其實是 1N**——而這件事在單線圖上完全看不出來，你的 DCIM 也永遠不會告訴你。
- **版本問題決定預算與時程。** 守表格 vs 做 HMA 差很多，而**兩版會並存好幾年**（IFC 2024 引用的仍是 2023 版文字）。這不是「哪個對」，是「這裡採用哪個」——**答案要當資料存進 `CodeRule.edition`。**
- **UL 9540A 那題有標準答案的陷阱。** 它是 test method 不是認證，**任一層沒觀察到火焰傳播就可以停止**——所以報告完全可能只做到 module 層，整櫃從沒被燒過，卻被當成「整套系統通過」。只有 unit 或 installation 層的結果才足以支撐小於 3 ft 的間距宣告。
- **間距不要搬美規數字**：NFPA 855 的 **3 ft（0.9 m）量的是 unit 與 unit**；台灣指引的 **30 m** 量的是 ESS 與周邊建物道路（有 2 小時防火牆＋自動滅火可縮到 3 m）。**差 33 倍，因為量的根本不是同一件事。**
- **排風機那題是消防對電力樹提出的容量需求**（2026 版 §4.10 要求關鍵安全系統有 NFPA 110／111 緊急電源）。**跟 W32 那題「冰水主機接 UPS 還是直吃發電機」是同一個形狀，建議一起問。**

### Q3 — 問 **STS 供應商 / 控制系統承包商**（⚠️ commissioning 前，設定值一旦交機就沒人再動）

> 「**轉換演算法設的是快速（1/4 cycle）還是抗湧流（3/4 cycle）？下游有沒有變壓器型 PDU？**
> **高負載電流抑制門檻設多少、出廠值調過嗎？**
> **Retransfer 設 Yes 還是 No、延遲幾秒？**
> **SCR 的 latched 告警現場怎麼 reset、誰有權限、有沒有留記錄？**
> 還有——**你報的 MTBF，邊界畫在哪裡？** 含不含輸出斷路器？含不含**旁路操作的人為誤動作**？
> 最後：**兩條輸入往上追，到哪一層才真的分開？** 請畫到共同祖先為止。」

**為什麼是這題**：

- **前三個都是設定值，不是規格值**，而且**交機之後不會有人再看**。演算法決定 ride-through 餘裕是 13.83 ms 還是 3.00 ms；抑制門檻決定下游故障時 STS 凍結的範圍。
- **latched reset 流程決定你能不能信任「告警消失 = 問題解決」。** 如果現場可以隨手 reset 而不留記錄，那 `redundancy_effective()` 讀到的東西就是假的——**這題直接決定連貫性檢視 #1 那段程式碼有沒有意義。**
- **MTBF 那題是為了化解來源分歧而設計的問法。** WP 62 說 40 萬–100 萬小時、PDI 說超過 200 萬，兩邊差 2–5 倍。**別問「STS 可不可靠」（會得到行銷答案），問「你的 MTBF 邊界畫在哪」。** WP 62 把**人為誤操作**列為主要失效模式之一，而它不會出現在任何規格書的 MTBF 裡——對方要嘛給你精確定義，要嘛答不出來，**兩種結果都有用。**
- **最後一題是 `dc-10b` 的預習**，但現在問比較好：**設計還能改的時候問，比蓋完之後做稽核報表有用得多。**

### 這週沒選上、但別忘記的

- **容量測試那天的替代供電路徑寫在哪份 MOP 裡？窗口算到放電結束還是算到充飽？**（放電只佔 0.5–1 h，**再充電要 8–24 h**，總窗口 10–27 h。只鎖放電那段的排程系統，會在再充電期間放行另一路的維護——**那時兩路都沒有電池**。）
- **量內阻要不要把並聯串拉離線？**（IEEE 1188 建議要，串數少時誤差最明顯。所以**季測也該進同一套維護窗口衝突檢查**，它跟容量測試只有程度差別。）
- **STS 的設定真的不能從 BMS / DCIM 遠端改嗎？**（PDI 明訂不可。這是好事，但也代表 `preferred_source` 這種欄位在你的資料庫裡**永遠是副本**，要有定期比對機制。）
- **STS 的 512 筆事件記錄能不能拉出來、保存多久、有沒有波形圖？**（轉換只有幾毫秒，**沒有波形就查不出原因**；而 512 筆在一個不穩定的月份可能兩週就滾掉。）
- **鋰電那間房的樓板承重上限**（W33 Q3 提過，本週 `dc-09c` 的間距要求會改變佈局，兩題連動）。

**它的動手練習就是欠了四週的 `DeviceRegistry`**，所以這筆帳下週會被強制清掉。但請**先做連貫性檢視 #1**（`Alarm.latched`，約 30 分鐘），因為 `redundancy_effective()` 要讀它。

### 已經先查到、留給 `dc-10b` 的材料

本週為 `dc-10` 取材時多查到幾筆**專屬於「兩個源之間關係」**的東西，`dc-10` 卡片刻意沒用（那是 `dc-10b` 的範圍），先寄放在這裡免得重查：

- **IEC 62310-3 的 STS 效能碼 `XX YY B TS`** —— `XX` = 故障電流管理（`CB` 有整合斷路器／熔絲可開斷，`PC` 只能承受不能開斷）；`YY` = 中性線處理（`00` 無／`NC` 兩輸入中性線併接／`NS` 切換分離／`NI` 隔離變壓器分離）；`B` = 轉換型式（`B` break-before-make／`M` make-before-break）；`TS` = 電壓限值。**這四段應該原樣存成四個 enum 欄位，不要塞成一個 free-text 型號字串**——因為 `YY` 跟站點接地系統之間有硬約束（下一點）。
- **極數 × 接地系統是跨實體約束**（Socomec 技術文件的對照表）：TN-S 四線**強制 4W4P**（否則不平衡負載與接地阻抗差異會造成環流；有 RCD 時還會誤跳）；TN-C **禁止切換 PEN**；IT 有分佈中性線**必須 4W4P**，否則兩顆 IMD 並聯會量到阻抗下降而誤報。**這是 `dc-02` 阻抗決定 `dc-07b` 合法性之後，第二個「A 的欄位決定 B 的合法性」——而且這次是站點層級欄位決定設備層級合法性。**
- **來源分歧（BBM vs MBB）**：Socomec 明說 Statys 預設且建議 **BBM**，MBB「技術上可行但很少用，因為重疊兩個獨立源會產生不受控的環流」；但另有資料說同步源可以做 MBB（重疊不到一個週期）。**兩邊很可能在講不同的設備**——UPS **內部**的靜態開關（逆變器↔旁路，同一台 UPS 主動同步，Rehlko 明確描述 MBB 重疊導通）vs **獨立**兩源之間的 STS。**同樣叫「靜態開關」，同步前提完全不同。** 這正是 `dc-10b` 該處理的分歧。
- **相位同步窗有三個數字，而且量的是不同東西**：MBB 安全條件約 **5 電氣度**（另加電壓差 <5%、頻率差 <0.2 Hz）；一般 STS 可接受窗口 **10–20 電氣度**；Socomec 說 Statys 本體可在**高達 180°** 相位差下切換，但**負載未必受得了**（馬達、變壓器會出問題），所以提供「非同步時禁止轉換」的設定。**三個數字分別是「MBB 的安全條件」「典型設定」「設備本體能力」——不是同一個量，別放同一欄。**
- **4 極 STS 的中性線是刻意重疊的**（Socomec）：BBM 逐相進行，但中性線要**重疊不超過 10 ms** 以維持參考電位。所以「break-before-make」這個描述**對相線成立、對中性線不成立**。
- **可靠度數字第三個版本**：Socomec 給 λ_STS ≈ **150 FIT（MTBF 6.67×10⁶ h）**、λ_UPS ≈ 2860 FIT（35 萬 h）、λ_cable ≈ 1 FIT/m。**這跟 `dc-10` 已記錄的 WP 62（40 萬–100 萬 h）與 PDI（>200 萬 h）湊成三個版本**，`dc-10b` 可以用它算「加 STS 到底划不划算」——而關鍵在於**答案是上游共祖的函數，不是 STS 的函數**：兩條路徑若共用一個高失效率的祖先，STS 帶來的改善會從一個數量級塌到接近 1。**這正好是 `ancestors()` 那段程式碼的動機。**
