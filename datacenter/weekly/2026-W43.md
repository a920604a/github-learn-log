# 2026-W43 週報：觀察者也有拓撲

第十三份週報。本週 5 張卡、5 個工作日全齊（10-19 ~ 10-23），連續第二個滿週。內容上收掉第四輪「系統與協定」（[dc-42](../devices/bacnet-object-model.md) ~ [dc-45](../devices/protocol-gateway.md)），週五由 [topic-01](../topics/nameplate-derated-measured.md) 開第五輪主題卡。

W42 的母題是「裸值不是事實」：一個數字要帶著不確定度、年齡、時鐘、登記才是事實。這週往外推一層：**帶著那些限定語的數字，是某個觀察者交出來的；觀察者本身有路徑、有週期、有故障域——也就是有自己的拓撲，而且那張圖跟電力圖長得不一樣。** 電力 2N，可觀測性常常只有 N。

## 串起來

單張卡是點。這週有一條很乾淨的線：**四張協定卡是 topic-01「實測值」的上游，topic-01 是第四輪的下游出口。**

```text
伺服器 PSU ─┬─ BMC（dc-44，IPMI／Redfish）───────────────────────────┐
            └─ rack PDU outlet（dc-43，SNMP）────────────────────────┤
UPS ────────┬─ 網卡 NMC（dc-43，SNMP → IT）───────────────────────────┼─→ MEASURED ─×1.2─→ ALLOCATED
            └─ RS-485 Modbus → 閘道器（dc-45）→ BACnet/IP → BMS（dc-42）┘    （topic-01，容量帳本）
```

每一條路徑都有一種**「成功的錯誤」**——協定回成功、時間戳新鮮、值是錯的：SNMP 是 scale 錯一個 10 的次方（dc-43）、IPMI 是飽和在 1020 W（dc-44）、閘道器是 hold-last 與 Unit ID 指錯（dc-45）、BACnet 是 `Out_Of_Service` 時被人鎖住的值（dc-42）。

### 第一條線：高估會被抓，低估不會

topic-01 有兩個拿 kind 互相比對的告警：`ALLOCATION_BELOW_MEASURED`（配額 < 實測）與 `MEASURED_ABOVE_NAMEPLATE`（實測 > 銘牌）。把上游四種錯誤分方向看：

- **高估**（scale ×10、把 PSU 輸出側當輸入側卻除錯效率）→ 實測衝過銘牌 → `MEASURED_ABOVE_NAMEPLATE` 響，而且 topic-01 正確地把它歸為**資料品質**告警。
- **低估**（IPMI 飽和、DCMI 3 h 平均窗把 900 W 抹成 522.2 W、scale ÷10、hold-last 停在離峰值）→ **兩個告警都不響**。原因是結構性的：**配額是從實測算出來的**，錯誤同時流進比較式的兩邊。

算一次（以下是我把 dc-44 與 topic-01 的數字接起來，卡片沒有這個情境）：伺服器 PSU 1600 W、真實峰值 1400 W，IPMI SDR M=4 → 讀值卡在 **1020 W**。配額 1020 × 1.2 = 1224 W → 1288.4 VA（PF 0.95）→ 一具 8 646 VA 的 PDU 放 **6 台**。真實負載 6 × 1400 / 0.95 = **8 842 VA**，超過降載上限 **195.7 VA（2.3%）**——超的是 [dc-14](../devices/rack-pdu.md) 的 80% 連續負載線。`ALLOCATION_BELOW_MEASURED`：1224 > 1020，不響；`MEASURED_ABOVE_NAMEPLATE`：1020 < 1600，不響。照銘牌放只會是 5 台。

**唯一抓得到的是第二個觀察者。** 若那具 PDU 有計量，它讀到 ≈ 8 400 W，而 Σ BMC 只有 6 × 1020 = 6 120 W，殘差 2 280 W → dc-44 的 `RACK_POWER_UNRECONCILED`。所以 dc-44 的「兩個觀察者看同一條電」不是冗餘浪費，是**低估方向唯一的防線**；dc-44 的 `SERVER_POWER_UNATTRIBUTED` 把「至少一條路徑」當合格，對這個問題是不夠的——**能對帳要兩條**。

### 第二條線：觀察圖有自己的故障域

dc-45 的 `GATEWAY_SPANS_REDUNDANT_PAIR`（A／B 路 UPS 的點位走同一顆閘道器）是全軌跡**第一次把電力圖和觀察圖 join**。但同一個形狀其實四張協定卡都寫了，只是沒有命名：

| 卡 | 共用的觀察節點 | 掉了的樣子 |
|---|---|---|
| dc-42 | 一條 MS/TP trunk、一個沒 BBMD 的子網路 | 整條 trunk 或整個子網路一起消失 |
| dc-43 | 一台 trap receiver、一組 community／v3 帳號 | 所有 trap 消失而**輪詢照常**、儀表板正常；或一整批同設定的設備同時消失 |
| dc-44 | 管理網、一組 BMC 帳密 | 整批 BMC 同時失明；管理網被打穿則能開關機 |
| dc-45 | 一顆閘道器、一條 RS-485 | 後面整條總線失明，A／B 路一起 |

`Point.via` 目前只裝 gateway id（dc-45 意涵 1），所以 join 只看得到表格最後一列。這是本週連貫性 🔴2 與自我測驗 Q5 的來源。

### 第三條線：同一個「現在」差三個數量級

每條路徑的資料年齡：閘道器代理模式 5.92 s（死 3 台變 10.28 s）、BACnet MS/TP 讀 100 屬性 16.46 s、SNMP 60 s 輪詢、Redfish 500 台逐一爬 70 個 GET **262.5 s** 一輪。topic-01 的演算三說「先 sum 再 max」，`coincident()` 假設各序列的第 i 個樣本是同一時刻——跨這四條路徑，同一個 i 可能相差四分鐘以上（這是我的推論，卡片沒寫）。**同時峰值需要對齊的時間軸**，而對齊需要 dc-39 的 `clock_id` 與 dc-44 的 `ReadingTime`，不是 collector 的收到時間。

### 🔴 1. `Finding` 連續第三週沒有形狀，而「缺東西」已經十五個

W41 🔴1 提了 `Finding(code, subject_kind, subject_id, reason, kind)`，W42 沒落地，這週 dc-42 練習寫「`Finding(code, subject)` 有現成的就換掉」——**欄位名又跟 `core.py` 的 `Finding(code, space_id, reason)` 不同**。然後本週七個檢查函式全部回元組：`check_mstp`、`check_instances`、`check_subnets`（dc-42）、`check_snmp`（dc-43）、`check_bmc`（dc-44）、`check_gateways`（dc-45）、`check`（topic-01），型別都是 `list[(code, id)]`。

代價已經看得見：十五個「缺東西」告警（第十二到十五個是本週的 `SUBNET_NO_BBMD`、`UPS_NO_NOTIFICATION_PATH`、`SERVER_POWER_UNATTRIBUTED`、`POINT_VALIDITY_UNSIGNALED`）沒有 `kind` 可以聚合；topic-01 的 `MEASURED_ABOVE_NAMEPLATE` 自稱「資料品質告警，不得同時吐容量類告警」——**這句話在元組裡沒有欄位可以表達**。而 `uncovered()` 已經回 `(target_id, Result)`，`Result` 帶著 reason，到了 `Finding` 這一層卻被壓回字串。

**收斂建議**（約 10 分鐘）：

```python
class FindingKind(Enum): VIOLATION; MISSING_PROTECTION; DATA_QUALITY; FACT
@dataclass(frozen=True)
class Finding: code: str; subject_kind: str; subject_id: str; result: Result; kind: FindingKind
def from_uncovered(code, subject_kind, pairs) -> list[Finding]   # kind = MISSING_PROTECTION
```

`space_id` 刪除；`check_*` 一律回 `list[Finding]`。掛進 **`topic-02` 練習第 0 步**（80% 規則卡的檢查天然會產出 `VIOLATION` 與 `DATA_QUALITY` 兩種，正好驗這個欄位）。

### 🔴 2. `Point` 才統一一週，三張卡各長了欄位，沒有一張回頭改 `points.py`

dc-42 立的唯一 `Point(id, asset_id, role, protocol, native_ref, interval_s, last_attempt_ts_s, last_good_ts_s, quality, time_basis="poll", clock_id=None)`。之後：

- dc-44 意涵加 `side ∈ {input, output}`、`aggregation{kind: instant|avg|min|max, window_s}`，並要把 `resolution`／`range_max`「寫回 Point 的不確定度」。
- dc-45 意涵加 `via: list[gateway_id]` 與 **`age_bound_s`**，同時說 `poll_cycle_s`「是算出來的」——存一個由 `via` 與死設備數重算的值，就是 topic-01 剛批評的 NetBox `available_power`（[dc-02](../devices/transformer.md) 叫我們別做的那種）。
- `time_basis` 出現三個自由字串：`"poll"`（dc-41／42）、`"device"`（dc-44）、`"gateway_poll"`（dc-45）。
- topic-01 的 MEASURED 存 `(node_id, window, statistic, point_ids)`——跟 dc-44 的 `aggregation{kind, window_s}` **是同一個概念、兩組名字**（`statistic`／`kind`、`window`／`window_s`）。

**收斂建議**（約 15 分鐘）：

```python
class TimeBasis(Enum): POLL; DEVICE; GATEWAY_POLL
@dataclass(frozen=True)
class Aggregation: stat: Literal["instant","avg","min","max","p95","peak"]; window_s: float | None
# Point 新增：via: tuple[HopRef, ...] = ()、tap: Literal["psu_input","psu_output"] | None、
#            aggregation: Aggregation = Aggregation("instant", None)、resolution、range_max
def age_bound_s(point, hops, now_s) -> float      # 派生，不存
```

topic-01 的 MEASURED `Figure.basis` 直接放 `Aggregation`＋`point_ids`，不另起名字。`via` 的元素是 `HopRef(kind, id)` 而不只是 gateway id——理由見「串起來」第二條線與 Q5。掛進 **`topic-03`（N／N+1／2N）練習第 0 步**：冗餘定義那張卡正好需要「觀察路徑也要算冗餘」這個查詢。

### 🟡 4. `Reason` 剛定案，`UNSOURCED` 就被拿去裝三件事

W42 定義 `UNSOURCED` = 「只有搜尋摘要、沒有可用出處」。本週：dc-44 意涵 4「side 未知 → UNSOURCED」、dc-45 驗收 #13「hold-last → UNDETERMINED(UNSOURCED)」、dc-44 `bmc_psu`「side None → UNDETERMINED」（沒寫 reason）。side 未知是**缺輸入**（`MISSING_INPUT`）；hold-last 是**有值但無法驗證有效性**，四個既有 reason 都不貼切。**建議**：side 未知改 `MISSING_INPUT`；新增 `Reason.VALIDITY_UNSIGNALED`（給 hold-last）與 `Reason.SATURATED`（給 dc-44 讀值 = `range_max`——它不是精度不夠，是**只知道下界**，見「串起來」第一條線）。

### 🟡 5. 假設值仍在預設參數裡（W42 🟡5 未清）

## 自我測驗

**Q1.〔事實回憶，dc-43〕** UPS-MIB `upsOutputSource` 讀到 4 是什麼狀態？5 呢？為什麼有人會搞反？另外，一個 Counter32 前值 4,294,966,000、本值 1,500：`sysUpTime` 上升時差值多少？`sysUpTime` 下降時呢？

??? note "答案"
    **4 = bypass、5 = battery**（RFC 1628 SYNTAX；同一份 RFC 的 MODULE-COMPLIANCE 段寫成 normal(2)／battery(4)，Errata 4831 裁定 SYNTAX 正確，observium 照抄了錯的版本）。
    繞回：`1500 + 2³² − 4,294,966,000 = 1500 + 1296 =` **2796**。`sysUpTime` 下降表示重開機，差值**丟棄**、重新取基準，不是繞回。
    **對你的模型**：enum 對照存成有出處的 `MibObject.enum_map`（帶 `errata_applied`）；差值函式回三態 `OK／WRAP／DISCONTINUITY(REBOOT|RESET)`，每台 agent 要另存 `AgentState.uptime_ticks`，能量帳本把 DISCONTINUITY 區間標為缺口、不補零。

**Q2.〔事實回憶，dc-42〕** 一個 CRAH 冰水閥 AO，`Relinquish_Default` = 50 %。優先序 16 = 30 %、12 = 55 %、8 = 90 %。有效值是多少？值班員放開 8 之後呢？接著 BMS 寫 16 = 45 %，有效值變不變？再放開 12 呢？

??? note "答案"
    **90 %（8）** → 放開 8 → **55 %（12）** → BMS 寫 16 = 45：寫入成功，**有效值仍 55 %**（12 比 16 優先）→ 放開 12 → **45 %（16）**。全部放開才回到 50 %。
    **對你的模型**：命令是 `CommandSlot{point_id, priority, value, writer, written_ts_s}` 的集合，有效值是查詢結果；「WriteProperty 回成功」不能當作「閥到位」，`COMMAND_OVERRIDE_STALE` 由 `priority ≤ 8` 與 `written_ts_s` 推導。

**Q3.〔應用，dc-45〕** 一條 RS-485 掛 24 台電錶（每台一次交易 45.83 ms），閘道器代理模式、序列側 timeout 400 ms × attempts 3，上層每 5 s 讀一次。最多容忍幾台死設備？死到上限時健康設備的最壞資料年齡是多少？collector 的 timeout 至少要設多少？

??? note "答案"
    健康一輪 24 × 45.83 = **1100 ms**；每台死設備多花 1200 − 45.83 = 1154.17 ms。`1100 + n × 1154.17 ≤ 5000` → n ≤ 3.38 → **3 台**（3 台 4562.5 ms，4 台 5716.7 ms）。3 台死時最壞年齡 4.5625 + 5 = **9.56 s**。
    collector timeout 要 **> 400 × 3 = 1200 ms**（透通模式再加佇列中最長等待），否則例外碼 11 會被記成 TIMEOUT、排查方向錯成「網路掛了」→ `TIMEOUT_NOT_NESTED`。
    **對你的模型**：`age_bound_s` 由 `via` 每一跳的 `cycle_ms(n_ok, n_dead)` 派生（不存）；`n_dead` 來自同閘道器後方點位的 `quality`，所以一台設備的品質會改變**別台**點位的年齡上界。

**Q4.〔應用，跨 dc-44 × topic-01〕** 一櫃 rack PDU 降載後 8 646 VA，PF 取 0.95。伺服器 PSU 銘牌 1600 W，真實峰值 1400 W，但 BMC 的 IPMI SDR 功率感測器 M=4。你用「實測峰值 × 1.2」做配額。一具 PDU 放幾台？真實負載超不超？topic-01 的四條告警哪條會響？什麼能抓到？

??? note "答案"
    M=4 上限 4 × 255 = **1020 W**，讀值飽和。配額 1224 W → 1288.4 VA → ⌊8646/1288.4⌋ = **6 台**。真實 6 × 1400/0.95 = **8 842 VA**，超降載上限 195.7 VA（**2.3%**）。（照銘牌只會放 5 台。）
    `ALLOCATION_BELOW_MEASURED`（1224 > 1020）不響、`MEASURED_ABOVE_NAMEPLATE`（1020 < 1600）不響——配額由實測算出，錯誤同時流進兩邊。能抓到的是**第二個觀察者**：PDU 計量讀到約 8 400 W vs Σ BMC 6 120 W，殘差 2 280 W → `RACK_POWER_UNRECONCILED`。
    **對你的模型**：`Point.range_max`（由 SDR 的 x=255 推出），讀值 = `range_max` 時該樣本只是**下界**——`Result(UNDETERMINED, SATURATED)`（本週 🟡4 建議新增的 reason），不得進 `measured_peak()`；`SERVER_POWER_UNATTRIBUTED` 之外，容量用途還需要「有兩條路徑可對帳」的覆蓋等級。

**Q5.〔建模判斷，跨 dc-42 ~ dc-45〕** dc-45 的 `GATEWAY_SPANS_REDUNDANT_PAIR` 只檢查「冗餘配對共用閘道器」。請把它推廣成一個查詢：找出**任何**冗餘配對的觀察路徑共用的節點。你需要哪些資料？`Point.via` 要改成什麼？哪些共用不該算問題？

??? note "答案"
    以下是我的設計建議，不是卡片原文。
    **資料**：`Point.via` 改成有序的 `HopRef(kind, id)` 清單，`kind ∈ {gateway, bus, trunk, subnet, mgmt_net, collector, trap_receiver, credential_set}`——本週四張卡各自點名了其中幾種（「串起來」第二條線的表）。電力側沿用 `Asset.redundancy_peer`。
    **查詢**：對每一組冗餘配對 (A, B) 的同類關鍵點位（例：轉電池狀態），若 **A 的每一條有效觀察路徑都經過某個 hop h，B 的每一條也都經過 h**——h 同時是兩邊的單點——出 `OBSERVATION_SPOF_SPANS_PAIR(h)`。只有一條路徑時退化成 dc-45 的版本。
    **不該算問題的**：(1) 那個點位另有一條不經該 hop 的有效路徑（例：UPS 同時有 SNMP 與 Modbus，見本週 `UPS_NO_NOTIFICATION_PATH` 兩種 kind）——所以判斷要在 `Coverage` 層做，不是在單一 `Point` 上；(2) 共用的是 `credential_set` 但設備在不同網段——仍是共因（帳號被鎖兩邊一起消失），**應該算**，容易被誤排除。
    結構上這是 [dc-10b](../devices/sts-two-source-relationship.md) 共祖測試在觀察圖上的對偶：電力圖問「兩路有沒有共同上游」，觀察圖問「兩個證人有沒有共同的嘴」。

### 抽 W41 的 [dc-34 門禁與門控制器](../devices/access-control-door-controller.md)（2026-10-07，18 天前）

**題目**：機房有 40 扇 fail-safe 電磁鎖，每扇 500 mA。鎖的總電流多少？若鎖電源不在 UPS 上，市電中斷那一刻會發生什麼？用本週 topic-01 的語言，這 500 mA 是哪一種數字，40 扇直接相加可以嗎？另外，Wiegand 26 位元為什麼不能拿「卡號」當身分鍵？

??? note "答案"
    `40 × 0.5 =` **20 A**。不在 UPS 上 → fail-safe 斷電釋放 → **40 扇門同時打開**。

    **對你的模型**：`Door.lock_mode` ＋ 鎖是 `PowerFeed` 下游的消費者（電力圖的邊）；`EGRESS_BLOCKED_ON_POWER_LOSS` 由 `is_egress_path ∧ fail_secure ∧ ¬mech_egress` 推導；沒有 DPS 的門 → `DOOR_UNMONITORED`（第四個「缺東西」，本週 🔴1 的 `MISSING_PROTECTION` 家族）。

### 抽 W39 的 [dc-29 機櫃與 U](../devices/rack-and-rack-unit.md)（2026-09-25，30 天前）

**題目**：一個 OCP ORv3 44OU 機櫃的可用高度等於幾個 EIA U？為什麼不存在整數答案？一個 42U 櫃裝滿盲板，片間縫 1/16″ 時前面等效開了多少 U？用 IEC 60297 公差 0.4 mm 算呢？這和本週 topic-01 的 NetBox 預設值陷阱是同一種病嗎？
